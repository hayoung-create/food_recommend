# PRD - NutriPick : 건강 목표 기반 가공식품 추천 서비스

---

# 서비스 아이디어

사용자가 자신의 건강 목표(다이어트, 고단백, 저염식, 저당식)를 선택하면 식품의약품안전처 식품영양성분 데이터를 분석하여 해당 목표에 적합한 가공식품을 추천하는 웹 서비스.

추천 결과와 함께 영양성분, 추천 이유, 영양성분 시각화를 제공하여 사용자가 제품을 쉽게 비교하고 선택할 수 있도록 한다.

---

# 대상 사용자

- 건강한 식습관을 원하는 일반 소비자
- 다이어트 중인 사용자
- 운동을 하며 고단백 식품을 찾는 사용자
- 나트륨 또는 당류 섭취를 줄이고 싶은 사용자
- 가공식품을 구매하기 전에 영양성분을 비교하고 싶은 사용자

---

# 사용자가 겪는 문제

- 가공식품 종류가 너무 많아 어떤 제품을 선택해야 하는지 어렵다.
- 영양성분표를 직접 비교하기 번거롭다.
- 자신의 건강 목표에 맞는 제품을 찾기 어렵다.
- 칼로리, 단백질, 나트륨, 당류 등을 종합적으로 비교하기 어렵다.

---

# 제공할 핵심 가치

- 건강 목표에 맞는 가공식품을 빠르게 추천
- 영양성분을 한눈에 확인 가능
- 추천 이유를 함께 제공하여 선택을 돕는다.
- 공공데이터를 활용한 신뢰성 있는 추천 서비스

# 주요 기능

## 1. 건강 목표 선택

사용자는 아래 목표 중 하나를 선택한다.

- 다이어트
- 고단백 식단
- 저염식
- 저당식

## 2. 추천 시스템 (알고리즘 상세)

### 2-0. 카테고리(식품분류) 선택 흐름

건강 목표 선택 후, 사용자는 **식품분류(카테고리)**를 선택하여 해당 카테고리 안에서만 추천을 받을 수 있다.

**흐름**
1. 건강 목표 선택 (예: 다이어트)
2. 식품분류 목록 표시 (API 데이터에 존재하는 분류값을 동적으로 추출)
3. 사용자가 하나의 분류 선택 (예: 면류) — 선택 사항
4. **선택한 분류에 속한 제품만** 대상으로 점수 계산 후, 점수 높은 순으로 정렬한다.

**카테고리의 역할**
- 카테고리는 **추천 후보 집합을 필터링**한다.
- 영양소 점수 기준값(분위수 앵커)은 전체 DB(100g 기준) 분포 분석으로 고정된 상수를 사용한다.
- 카테고리 미선택 시: 전체 식품을 대상으로 동일 점수 체계를 적용한다.
- 선택한 카테고리 제품 수가 5개 미만이면 "해당 분류 제품 수가 적어 비교 결과가 제한적일 수 있습니다" 안내를 표시한다.

### 2-1. 데이터 기준
- **모든 영양성분 비교는 100g(또는 100ml) 기준으로 통일한다.**
  - 식약처 DB 값을 1회 제공량으로 재환산하지 않는다.
- 결측값이 있는 항목은 해당 항목 점수를 0으로 처리하고, 상세에는 "정보 없음"으로 표기한다. (제품을 추천 대상에서 제외하지 않음)

### 2-2. 점수 계산 흐름

```
1) 영양소별 점수 (0~100)
2) 건강목표별 가중치 가중합
3) 건강목표별 패널티 차감
4) 최종 recommend_score = round(clamp(가중합 - 패널티, 0, 100))
```

구현 모듈 (`backend/services/`):
- `nutrition_thresholds.py` — DB 분포·점수 앵커
- `nutrition_weights.py` — 목표별 가중치
- `nutrition_penalty.py` — 단일·복합 패널티
- `nutrition_score.py` — 영양소/목표별 점수 함수
- `recommendation.py` — 카테고리 필터·정렬 오케스트레이션

### 2-3. 영양소별 점수 (0~100)

기준값은 임의 상수가 아니라 **현재 DB(100g) 분포**에서 산출한다.  
분석 지표: 평균, 중앙값, 최소/최대, p10, p25, p75, p90

**높을수록 좋은 항목 — 단백질**
- p25 이하 → 0점
- p90 이상 → 100점
- 사이는 선형 보간

**낮을수록 좋은 항목 — 열량, 탄수화물, 지방, 당류, 나트륨, 포화지방, 콜레스테롤**
- p25 이하 → 100점 (콜레스테롤만 p25=0이라 p10~p90 사용)
- p90 이상 → 0점
- 사이는 선형 보간

#### DB 분포 요약 (분석 시점 products 100건, 100g 기준)

| 영양소 | 평균 | 중앙값 | p25 | p90 |
|--------|------|--------|-----|-----|
| 열량(kcal) | 200.6 | 179.5 | 145.8 | 314.5 |
| 단백질(g) | 6.0 | 5.7 | 4.0 | 9.7 |
| 탄수화물(g) | 30.7 | 27.2 | 20.5 | 51.8 |
| 지방(g) | 6.0 | 4.2 | 2.0 | 13.5 |
| 당류(g) | 4.1 | 1.2 | 0.1 | 12.6 |
| 나트륨(mg) | 273.4 | 241.0 | 176.8 | 458.1 |
| 포화지방(g) | 1.7 | 0.8 | 0.3 | 4.3 |
| 콜레스테롤(mg) | 25.6 | 15.8 | 0.0 | 59.5 |

데이터 추가 수집 시 `nutrition_thresholds.py`의 통계·앵커를 재분석하여 갱신한다.

### 2-4. 목표별 가중치

| 목표 | 열량 | 단백질 | 당류 | 지방 | 포화지방 | 나트륨 | 탄수화물 | 콜레스테롤 |
|------|------|--------|------|------|----------|--------|----------|------------|
| 다이어트 | 35% | 30% | 15% | 10% | 5% | 5% | - | - |
| 고단백 식단 | 15% | 50% | 5% | 15% | 10% | 5% | - | - |
| 저염식 | 10% | 5% | 5% | - | 10% | 60% | - | 10% |
| 저당식 | 10% | 10% | 60% | 5% | - | - | 15% | - |

가중합 = Σ (영양소 점수 0~100 × 가중치)  
→ 결과는 이미 0~100 구간의 점수이다.

### 2-5. 목표별 패널티

단백질만 높다고 무조건 상위가 되지 않도록, DB 분위수(p75/p90) 기준으로 감점한다.  
같은 영양소에 여러 규칙이 있으면 **가장 큰 감점만** 적용하고, 복합 규칙은 추가 적용한다.

#### 다이어트
| 조건 | 감점 |
|------|------|
| 열량 ≥ p90 | −15 |
| 열량 ≥ p75 | −8 |
| 당류 ≥ p90 | −12 |
| 지방 ≥ p75 | −10 |
| 포화지방 ≥ p90 | −10 |
| 열량 ≥ p75 **그리고** 지방 ≥ p75 (복합) | −12 |

#### 고단백 식단
| 조건 | 감점 |
|------|------|
| 지방 ≥ p90 / ≥ p75 | −12 / −8 |
| 포화지방 ≥ p90 / ≥ p75 | −12 / −6 |
| 지방 ≥ p75 **그리고** 포화지방 ≥ p75 (복합) | −10 |

#### 저염식
| 조건 | 감점 |
|------|------|
| 나트륨 ≥ p90 / ≥ p75 | −25 / −10 |

#### 저당식
| 조건 | 감점 |
|------|------|
| 당류 ≥ p90 / ≥ p75 | −25 / −10 |
| 열량 ≥ p75 | −10 |
| 지방 ≥ p75 | −12 |
| 포화지방 ≥ p75 | −8 |
| 열량 ≥ p75 **그리고** 지방 ≥ p75 (복합) | −15 |

최종 점수 = clamp(가중합 − 패널티 합, 0, 100)  
`recommend_score = round(최종 점수)`

### 2-6. 동점 처리
최종 점수가 동일한 경우, 단백질 함량(g, 100g 기준)이 높은 순으로 우선한다.

### 2-7. 결과
점수가 높은 순으로 정렬하며, 목록은 페이지네이션(기본 10개)으로 제공한다. (초기 MVP 문구의 TOP5와 동일한 점수 정렬 원칙)

### 추천 이유 (자동 생성 규칙)

목표별로 가중치 상위 2개 항목의 **영양소 점수(0~100)** 가 70 이상이면 문구를 생성한다.  
패널티가 적용된 경우 참고 문구를 추가할 수 있다.

예시
- 단백질 함량이 높아 고단백 식단에 적합합니다.
- 단백질이 충분해 포만감 유지에 도움이 됩니다. (다이어트)
- 칼로리가 낮아 다이어트에 적합합니다.
- 나트륨 함량이 낮아 저염식에 적합합니다.
- 당류 함량이 낮아 당 섭취를 줄이는 데 적합합니다.
- 참고: 고열량·고지방 항목으로 일부 감점되었습니다. (패널티 적용 시)

조건에 해당하는 문구가 없을 경우 "종합적인 영양 균형을 고려하여 추천되었습니다."를 기본 문구로 사용한다.

# 사용할 데이터 또는 외부 API

## 공공데이터 — 식품의약품안전처 식품영양성분DB(OpenAPI)

**Base URL**
```
https://apis.data.go.kr/1471000/FoodNtrCpntDbInfo02/getFoodNtrCpntDbInq02?serviceKey=db20c698a11dfc09c395219bd220b166607ecb6296bb0387db0b9e88a4bfb55b&type=json

```

**요청 파라미터**

| 파라미터 | 설명 | 비고 |
|---|---|---|
| serviceKey | 인증키 | ⚠️ 아래 보안 항목 참고 |
| type | 응답 형식 | json |
| numOfRows | 페이지당 결과 수 | 100 권장 (API 최대치 확인 필요) |
| pageNo | 페이지 번호 | 1부터 시작, 전체 데이터 수집 시 반복 호출 |

**사용 컬럼**
- 식품명
- 식품분류
- 에너지(kcal)
- 탄수화물(g)
- 단백질(g)
- 지방(g)
- 당류(g)
- 나트륨(mg)
- 포화지방(g)
- 콜레스테롤(mg)

**데이터 수집 전략**
1. 최초 1회, 페이지네이션으로 전체 데이터를 순회 수집한다.
2. 수집한 데이터를 SQLite에 저장하고, 이후 서비스는 API를 실시간 호출하지 않고 로컬 DB를 조회한다.
3. API 호출 실패/타임아웃 시: 최대 3회 재시도 후 실패하면 에러 로그를 남기고 해당 페이지는 건너뛴다.
4. 데이터 갱신은 MVP 범위에서 수동 재수집으로 처리한다 (스케줄러 없음).

### 🔴 보안 — 서비스 키 관리
- serviceKey는 코드에 하드코딩하지 않는다.
- `.env` 파일에 `DATA_GO_KR_SERVICE_KEY`로 저장하고 `.gitignore`에 `.env`를 추가한다.
- **현재 대화에 노출된 키는 재발급을 권장한다.**

# 기술적 제약

- 의료 진단 서비스를 제공하지 않는다.
- 사용자의 건강 상태를 진단하지 않는다.
- 건강 목표를 기준으로 추천한다.
- 추천은 영양성분 데이터 기반으로 수행한다.
- 데이터 품질은 식품의약품안전처 OpenAPI에 의존한다.
- 첫 버전에서는 단순하고 이해하기 쉬운 추천 알고리즘을 사용한다.

# 성공 기준

- 사용자가 건강 목표를 선택할 수 있다.
- **추천 결과는 로컬 SQLite 조회 기준 3초 이내에 표시된다.** (최초 API 데이터 수집 시간은 별도, 서비스 운영 중 응답 속도 기준)
- 건강 목표에 맞는 추천 제품 TOP5를 제공한다.
- 제품 상세 페이지에서 영양성분과 추천 이유를 확인할 수 있다.

# 개발 순서 (Cursor 작업 지시)

1. 프로젝트 구조 생성 (frontend/backend 분리)
2. `.env` 기반 API 키 설정 및 데이터 수집 스크립트 작성 (페이지네이션 포함)
3. 수집 데이터 SQLite 저장 및 전처리 (결측치 처리, 100g 기준 통일)
4. 추천 알고리즘 구현 (영양소 점수 → 가중치 → 패널티 → 정렬)
5. FastAPI 엔드포인트 구현 (목표 선택, 식품분류 목록 조회, 카테고리 필터 추천, 검색, 상세 조회)
6. React 화면 구현 (목표 선택 → 추천 카드 → 상세 페이지)
7. Chart.js 시각화 구현
8. 반응형 UI 적용
9. README 작성 (API 키 설정 방법 포함)
