# PRD - NutriPick : 건강 목표 기반 가공식품 추천 서비스

---

# 서비스 아이디어

사용자가 자신의 건강 목표(다이어트, 고단백, 저염식, 저당식)를 선택하면 식품의약품안전처 식품영양성분 데이터를 분석하여 해당 목표에 적합한 가공식품을 추천하는 웹 서비스.

추천 결과와 함께 영양성분, 추천 이유, 영양성분 시각화를 제공하여 사용자가 제품을 쉽게 비교하고 선택할 수 있도록 한다.

---

# 대상 사용자

- 건강한 식습관을 원하는 일반 소비자
- 다이어트 중인 사용자
- 운동을 하며 고단백 식품을 찾는 사용자
- 나트륨 또는 당류 섭취를 줄이고 싶은 사용자
- 가공식품을 구매하기 전에 영양성분을 비교하고 싶은 사용자

---

# 사용자가 겪는 문제

- 가공식품 종류가 너무 많아 어떤 제품을 선택해야 하는지 어렵다.
- 영양성분표를 직접 비교하기 번거롭다.
- 자신의 건강 목표에 맞는 제품을 찾기 어렵다.
- 칼로리, 단백질, 나트륨, 당류 등을 종합적으로 비교하기 어렵다.

---

# 제공할 핵심 가치

- 건강 목표에 맞는 가공식품을 빠르게 추천
- 영양성분을 한눈에 확인 가능
- 추천 이유를 함께 제공하여 선택을 돕는다.
- 공공데이터를 활용한 신뢰성 있는 추천 서비스

# 주요 기능

## 1. 건강 목표 선택

사용자는 아래 목표 중 하나를 선택한다.

- 다이어트
- 고단백 식단
- 저염식
- 저당식

## 2. 추천 시스템 (알고리즘 상세)

### 2-0. 카테고리(식품분류) 선택 흐름

건강 목표 선택 후, 사용자는 **식품분류(카테고리)**를 선택하여 해당 카테고리 안에서만 추천을 받을 수 있다.

**흐름**
1. 건강 목표 선택 (예: 다이어트)
2. 식품분류 목록 표시 (예: 밥류, 면류, 국·탕류, 과자류, 음료류, 빵류 등 — API 데이터에 존재하는 분류값을 동적으로 추출하여 목록화)
3. 사용자가 하나의 분류 선택 (예: 면류)
4. **선택한 분류에 속한 제품들끼리만** 정규화 및 점수 계산을 다시 수행하여 상위 5개를 보여준다.

**핵심 원칙: 카테고리 내부 재정규화**
- 정규화(Min-Max)는 "전체 식품 대비"가 아니라 **선택된 카테고리 내 제품 집합 기준**으로 계산한다.
- 예: 라면류를 선택하면, 라면류 제품들의 칼로리/단백질/지방/당류/나트륨 각각의 최소~최대 범위 안에서 정규화 점수를 매긴다.
- 이렇게 해야 "라면 중에 그나마 건강한 라면"이라는 사용자 기대와 결과가 일치한다. (전체 식품 기준으로 계산하면 라면은 밥류나 음료류에 비해 구조적으로 불리해서 상위권에 거의 못 들 수 있음)

**카테고리 미선택 시 (기본 동작)**
- 카테고리를 선택하지 않고 목표만 선택한 경우, 기존처럼 전체 식품 대비 정규화로 TOP5를 보여준다.
- 카테고리 선택은 선택 사항(옵션)이며, 필수 단계는 아니다.

**최소 표본 수 처리**
- 선택한 카테고리에 속한 제품 수가 너무 적으면(예: 5개 미만) 정규화 의미가 떨어질 수 있으므로, 이 경우 화면에 "해당 분류 제품 수가 적어 비교 결과가 제한적일 수 있습니다" 안내 문구를 표시한다.

### 2-1. 데이터 기준
- **모든 영양성분 비교는 100g(또는 100ml) 기준으로 통일한다.**
  - 식약처 DB는 기본적으로 100g 기준 값을 제공하므로 별도 환산은 불필요하나, 응답 필드가 1회 제공량 기준인 항목이 있는지 초기 데이터 점검 단계에서 반드시 확인한다.
- 결측값이 있는 항목은 해당 항목 점수를 0으로 처리하고, 최종 카드/상세페이지에는 "정보 없음"으로 표기한다. (결측이라고 제품을 추천 대상에서 제외하지 않음)

### 2-2. 정규화 방식
제품 집합 내 Min-Max 정규화를 사용한다. 샘플이 10개 이상이면 **5~95 백분위**로 범위를 잡아 극단값의 영향을 줄인다.

```
정규화 점수 = clamp((값 - 하한) / (상한 - 하한), 0, 1)
```

- "낮을수록 가점"인 항목(칼로리, 지방, 당류, 나트륨)은 `1 - 정규화 점수`로 반전하여 사용한다.
- "높을수록 가점"인 항목(단백질)은 정규화 점수를 그대로 사용한다.
- **다이어트 목표의 단백질**은 절대량(g)이 아니라 **100kcal당 단백질(g)** 로 계산한다.

### 2-3. 목표별 가중치

| 목표 | 단백질 | 칼로리 | 지방 | 당류 | 나트륨 |
|---|---|---|---|---|---|
| 다이어트 | 10% (열량 대비) | 40% | 25% | 15% | 10% |
| 고단백 식단 | 70% (절대량) | - | 30% | - | - |
| 저염식 | - | - | - | - | 100% |
| 저당식 | - | - | - | 100% | - |

최종 점수 = Σ (정규화된 항목 점수 × 가중치)
최종점수는 0~100으로 환산한다.
recommend_score = round(score * 100)

### 2-4. 동점 처리
최종 점수가 동일한 경우, 단백질 함량이 높은 순으로 우선순위를 정한다.

### 2-5. 결과
점수가 높은 상위 5개 제품을 추천한다.

## 3. 추천 결과

건강 목표 선택 화면 하단 또는 다음 화면에 **식품분류 선택 UI**(칩/버튼 형태)를 배치한다. 카테고리를 클릭하면 해당 카테고리로 필터링된 TOP5가 즉시 갱신된다.

카드 형태로 표시

- 식품분류

### 추천 이유 (자동 생성 규칙)

목표별로 가중치 상위 2개 항목이 임계값을 넘으면 문구를 생성한다.

예시
- 단백질 함량이 높아 고단백 식단에 적합합니다. (고단백 목표, 단백질 정규화 점수 상위 구간)
- 열량 대비 단백질이 높아 포만감 유지에 도움이 됩니다. (다이어트 목표)
- 나트륨 함량이 낮아 저염식을 원하는 사용자에게 적합합니다. (나트륨 정규화 점수 하위 30% 이내일 때)
- 당류 함량이 낮아 당 섭취를 줄이고 싶은 사용자에게 적합합니다.

조건에 해당하는 문구가 없을 경우 "종합적인 영양 균형을 고려하여 추천되었습니다."를 기본 문구로 사용한다.

# 사용할 데이터 또는 외부 API

## 공공데이터 — 식품의약품안전처 식품영양성분DB(OpenAPI)

**Base URL**
```
https://apis.data.go.kr/1471000/FoodNtrCpntDbInfo02/getFoodNtrCpntDbInq02?serviceKey=db20c698a11dfc09c395219bd220b166607ecb6296bb0387db0b9e88a4bfb55b&type=json

```

**요청 파라미터**

| 파라미터 | 설명 | 비고 |
|---|---|---|
| serviceKey | 인증키 | ⚠️ 아래 보안 항목 참고 |
| type | 응답 형식 | json |
| numOfRows | 페이지당 결과 수 | 100 권장 (API 최대치 확인 필요) |
| pageNo | 페이지 번호 | 1부터 시작, 전체 데이터 수집 시 반복 호출 |

**사용 컬럼**
- 식품명
- 식품분류
- 에너지(kcal)
- 탄수화물(g)
- 단백질(g)
- 지방(g)
- 당류(g)
- 나트륨(mg)
- 포화지방(g)
- 콜레스테롤(mg)

**데이터 수집 전략**
1. 최초 1회, 페이지네이션으로 전체 데이터를 순회 수집한다.
2. 수집한 데이터를 SQLite에 저장하고, 이후 서비스는 API를 실시간 호출하지 않고 로컬 DB를 조회한다.
3. API 호출 실패/타임아웃 시: 최대 3회 재시도 후 실패하면 에러 로그를 남기고 해당 페이지는 건너뛴다.
4. 데이터 갱신은 MVP 범위에서 수동 재수집으로 처리한다 (스케줄러 없음).

### 🔴 보안 — 서비스 키 관리
- serviceKey는 코드에 하드코딩하지 않는다.
- `.env` 파일에 `DATA_GO_KR_SERVICE_KEY`로 저장하고 `.gitignore`에 `.env`를 추가한다.
- **현재 대화에 노출된 키는 재발급을 권장한다.**

# 기술적 제약

- 의료 진단 서비스를 제공하지 않는다.
- 사용자의 건강 상태를 진단하지 않는다.
- 건강 목표를 기준으로 추천한다.
- 추천은 영양성분 데이터 기반으로 수행한다.
- 데이터 품질은 식품의약품안전처 OpenAPI에 의존한다.
- 첫 버전에서는 단순하고 이해하기 쉬운 추천 알고리즘을 사용한다.

# 성공 기준

- 사용자가 건강 목표를 선택할 수 있다.
- **추천 결과는 로컬 SQLite 조회 기준 3초 이내에 표시된다.** (최초 API 데이터 수집 시간은 별도, 서비스 운영 중 응답 속도 기준)
- 건강 목표에 맞는 추천 제품 TOP5를 제공한다.
- 제품 상세 페이지에서 영양성분과 추천 이유를 확인할 수 있다.
- 영양성분 그래프를 통해 제품을 쉽게 이해할 수 있다.
- MVP를 6~8시간 내 구현 가능한 수준으로 완성한다. (데이터 정제 단계 변수 고려하여 기존 5~6시간에서 상향)

# 개발 순서 (Cursor 작업 지시)

1. 프로젝트 구조 생성 (frontend/backend 분리)
2. `.env` 기반 API 키 설정 및 데이터 수집 스크립트 작성 (페이지네이션 포함)
3. 수집 데이터 SQLite 저장 및 전처리 (결측치 처리, 100g 기준 통일)
4. 추천 알고리즘 구현 (정규화 → 가중합 → 상위 5개 추출)
5. FastAPI 엔드포인트 구현 (목표 선택, 식품분류 목록 조회, 카테고리별 재정규화 추천, 검색, 상세 조회)
6. React 화면 구현 (목표 선택 → 추천 카드 → 상세 페이지)
7. Chart.js 시각화 구현
8. 반응형 UI 적용
9. README 작성 (API 키 설정 방법 포함)
